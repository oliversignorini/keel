# Keel — state of the repo, August 2026

A review of what is actually built against what the Notion project says is
built, and the resequenced plan that comes out of it. Written at `14f7808`.

This closes the Notion task "Keel Phase 10 — Architecture review and
implementation plan". Everything below either states a verified fact about

## 1. What is built

Phases 0–8 are merged and the claim holds up. Measured, not assumed:

|                                  |                                                                                                                                |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Django apps                      | 11 — `accounts` `audit` `billing` `connections` `core` `files` `jobs` `notifications` `organizations` `widgets`, plus `config` |
| Python under `apps/api/keel`     | 15,341 lines                                                                                                                   |
| TypeScript under `apps/web`      | 8,685 lines                                                                                                                    |
| Python test files                | 70                                                                                                                             |
| Production viewsets / `APIView`s | 19                                                                                                                             |
| Generated TS client              | 11,229 lines, regenerated and diffed in CI                                                                                     |
| CI jobs                          | 7 — lint, typecheck, test-api, test-web, api-client-generation, e2e-accessibility, contracts                                   |

The invariants the README advertises are real and enforced, which is the
single most important finding here — the interesting parts of this repo are
not decoration:

- `keel/core/authz.py` registers every `GlobalViewSet` and `OrgScopedViewSet`
  subclass at import time via `__init_subclass__`, and refuses at import
  time to let one exist without `required_permissions` and either
  `organization_scoped = True` + `test_factory` or a `GLOBAL_JUSTIFICATION`.
- `keel/organizations/tests/test_meta_router_wiring.py` fails if a scoped
  viewset exists that the tenant-isolation walk cannot reach — the router
  itself cannot silently go unwired.
- `tenant_isolation.py` builds a row in org A, gives an org-B member every
  required permission, and asserts **404, not 403**.
- Per-directory coverage floors in `[tool.keel.coverage]`, enforced by
  `scripts/check_coverage.py`, with 100% floors on the authz, audit, credit
  and crypto modules.
- `contracts` job runs `lint-imports` and re-derives `openapi.merged.json`,
  failing on drift.

Phase 8's observability work is in: Sentry on both runtimes with
`send_default_pii: False`, PostHog, DRF throttling with `Retry-After`,
security headers, `axe-core` in Playwright, a k6 smoke test, staff
impersonation with service-layer restrictions.

## 3. Real gaps found

Things that do not exist and should, in rough order of embarrassment if the
repo went public today:

**Repository is not presentable.** No `LICENSE` — which makes "open-source
release" legally meaningless. No `SECURITY.md`, `CONTRIBUTING.md`,
`CHANGELOG.md`, issue templates, or PR template. No Dependabot or Renovate
config, so the dependency-freshness claim has nothing behind it.

**`README.md:68` links to `docs/architecture.md`, which does not exist.**
The README sends a first-time reader to a 404 to find "the full seven"
invariants. There is no architecture diagram and no auth request-flow
diagram anywhere in the repo.

**No `CLAUDE.md` and no `.claude/`.** The PRD's Phase 9 specifies eight
slash commands (`/new-resource`, `/new-job`, `/check-invariants`, …) and an
agent-facing rules file. Neither exists, so every agent working in this repo
rediscovers the invariants from scratch — as this session did.

**CI is missing its production and security gates.** `manage.py check
--deploy` appears only as an unticked checkbox in `docs/plans/phase-0.md`
and `phase-1.md`; it has never run in CI. No Bandit, no `pip-audit`, no
`pnpm audit`, no secret scanning. `SECRET_KEY` falls back to
`"insecure-dev-key-change-me"` with no guard that prod cannot boot on it.

**No query-count tests anywhere.** `grep` for `assertNumQueries` /
`django_assert_num_queries` across `apps/api` returns nothing. Every list
endpoint is one careless `select_related` removal away from an N+1 that
nothing catches.

**No unsafe-rendering guardrail.** One `dangerouslySetInnerHTML` exists
(`components/json-ld.tsx`, correctly justified in a comment), but nothing
stops the next one. No lint rule, no sanitizer wrapper.

**`scripts/init.ts` does not exist.** Keel is a working application, not yet
a template. The README says so honestly.

## 4. The architecture decision

Notion left one architecture question open: Django Ninja instead of DRF, or
an explicit rejection. That is now decided — **migrate to Ninja** — and the
inspection, the cost, and the argument that was made against it are all
recorded in [`docs/adr/0001-django-ninja-over-drf.md`](adr/0001-django-ninja-over-drf.md).

It is the single biggest structural change left in Keel, and it dominates
the sequencing below: everything that touches a view has to wait for it, or
be written twice.

### How the waves parallelise

**Wave 1 — four worktrees, right now, no conflicts.** Phase 9 splits into
9.A repo meta-files, 9.B architecture docs and diagrams, 9.C CI security
gates, 9.D `CLAUDE.md` and slash commands. Each owns a disjoint set of paths
(listed in `docs/plans/phase-9.md`) and none of them touches `apps/`. This
is the wave to start with: it is what makes the repo survive a stranger's
first thirty seconds, and it can run while Phase 10 is still being read.

**Wave 2 — one worktree, serialised.** The Ninja migration. While it runs,
**no other worktree may add or change a view, serializer, route, or
generated-client call site.** Phase 12 is the only thing safe to run
alongside it, because it touches `infra/`, settings and docs only.

**Waves 3–5 — the foundations, then the hardening pass.** 11 and 12 can
share a wave. 13, 14 and 15 are three genuinely independent apps
(`files`, `billing`, `jobs`+`audit`) and are the best parallel wave after
Phase 9. Phase 16 splits three ways (query hygiene, boundaries, indexes) but
must follow them, since it adds query-count tests over endpoints 13–15 are
still changing.

**Wave 6 — serial, and last.** `init` rewrites everything; the release pass
follows it.

### Rules that keep parallel worktrees from colliding

Every plan file carries an explicit **Boundary** section naming what the
worktree owns and what it must not touch. Three rules hold across all of
them:

1. **`keel-prd.md`, `docs/plans/*`, `docs/adr/*` and `docs/review-*.md`
   belong to the orchestrator.** A worktree that wants one changed says so
   in its report instead of editing it.
2. **No migrations outside a phase that declares one.** The schema is one
   baseline migration; a migration in a feature branch is drift until proven
   otherwise.
3. **One worktree at a time may regenerate `openapi.merged.json` or
   `packages/api-client/src/generated`.** Two cannot; the CI drift gate
   turns that into an unresolvable conflict.

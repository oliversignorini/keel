# Phase 20 — `Widget.status` becomes a real choice field

**Source of truth:** this file, plus the 19.C review finding it records.
**Depends on:** Phase 19 merged (`fe5fce6`).
**Size:** Small. One slice, one migration.

---

## What this is

Slice 19.C made `apps/web/app/(app)/app/[org]/widgets/` a render of
`templates/ui`, and in doing so the reference slice lost its status UI:
`widget-status-field.tsx`, its unit test, and `apps/web/lib/widgets/status.ts`
were deleted, and `status` became a plain text input plus a raw table cell.

That was not a template limitation. `packages/cli`'s UI generator fully
supports choice fields — `<Select>` via `Controller`, `<Badge>` variants, a
per-field component file, a label helper — and CI's `Gizmo` fixture exercises
all of it. The reason `Widget` didn't get it is narrower: `Widget.status` is
declared as

```python
status = models.CharField(max_length=32, blank=True, default="")
```

Rendering it as a `<Select>` requires generating it as `status:choice(...)`,
which puts `choices=` on the model, which `makemigrations --check` treats as
a schema change. Phase 19 declared no migration, so 19.C was correctly boxed
in and flattened the field instead.

**This phase declares that migration.** It exists so the reference slice —
the thing every downstream project sees as "what a generated resource looks
like" — shows the generator at full strength rather than at the strength one
phase's boundary happened to allow.

## Boundary

**In scope:** `apps/api/keel/widgets/**` (including a new migration),
`apps/web/app/(app)/app/[org]/widgets/**`, and the reference-slice field
spec in `.github/workflows/generators.yml`.

**Declared migration:** exactly one, against `widgets`, adding `choices` to
`Widget.status`. This is the only migration this phase may add, and it is the
`WORKTREES.md` rule 2 exception for it.

**Out of scope:** `packages/cli/**` and `templates/**` — the generator
already does this correctly and must not need changing. If it turns out it
does, that is the finding, and it belongs in the report before it belongs in
a diff. Also out of scope: any other app's models, and `keel-prd.md` /
`docs/plans/**` / `docs/adr/**`.

## Work

Choose the status values from what the deleted `lib/widgets/status.ts`
documented, since that file recorded the real intent:

```
draft, active, paused
```

with `draft` → `outline`, `active` → `success`, `paused` → `warning` as badge
variants, and title-case labels. Note the deleted file's comment: it rendered
an unrecognised value rather than dropping it. If the generated choice-field
component doesn't preserve that behaviour, say so in the report — the answer
may be that the template should, which would make this a `templates/` change
and a second phase.

Then:

1. Add `choices` to `Widget.status` and generate the migration with
   `makemigrations`. Do **not** hand-write it, and do **not** edit
   `0001_initial.py` — a second migration is the honest record of a change
   made after `v1.0.0` was tagged.
2. Update the reference-slice field spec in `generators.yml` from
   `status:str(32)?` to the choice form, so `reference-slice-is-a-render`
   regenerates what is committed.
3. Regenerate the reference slice, backend and frontend, and commit the
   result. The status `<Select>`, the `<Badge>` column, the per-field
   component file and its label helper should all come back — generated, not
   hand-written.
4. Confirm the widgets e2e and component tests still pass, and that the
   restored component carries test coverage equivalent to the deleted
   `widget-status-field.test.tsx`. If the generator emits the component but
   no test for it, that gap is worth reporting.

## The thing to watch

19.A established that `migrations/0001_initial.py` is never regenerated by
the generator — Django's writer timestamps it. A second migration in a
generated app is new territory: check that `reference-slice-is-a-render`
still passes with `0002_*` present, and that a `--force` regeneration
doesn't delete or rewrite it. If it does, that is a generator bug worth a
follow-up phase, not something to work around by hand-editing the render.
